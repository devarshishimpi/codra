<h2 id="workflow">Workflow</h2>

Contributions are welcome. The recommended workflow keeps changes focused and easy to review.

1. **Fork the repository** — Fork <a href="https://github.com/devarshishimpi/codra" target="_blank" rel="noopener noreferrer" className="text-primary hover:underline">github.com/devarshishimpi/codra</a> and clone your fork locally.
2. **Create a focused branch from main** — Name your branch descriptively — fix/webhook-signature or feat/model-config-ui, for example.
3. **Install dependencies** — `npm install` and copy `.dev.vars.example` to `.dev.vars` with your secrets filled in.
4. **Make your change** — Keep the scope tight. Prefer existing patterns over new abstractions.
5. **Run typecheck and tests** — `npm run typecheck` and `npm test` must both pass before opening a PR.
6. **Open a pull request** — Open your PR against the main branch. Write a clear description of what changed and why, and reference any related issues.

<Note type="info">
Before opening a PR against <code>main</code>, run <code>npm run typecheck</code> and <code>npm test</code>. Both must pass. PRs that break type coverage or existing tests will not be merged.
</Note>

<h2 id="conventions">Engineering Conventions</h2>

| Topic | Guideline |
| --- | --- |
| Scope | Keep changes focused and intentional. One logical change per PR. |
| Abstractions | Prefer existing patterns over new abstractions. Read adjacent code before introducing new helpers. |
| TypeScript | Full type coverage required. Use Zod schemas for runtime data boundaries, especially for external API responses. |
| Dashboard UI | Keep dashboard pages clear, dense, and operational. Avoid decorative complexity that reduces information density. |
| Secrets | Do not commit secrets, .dev.vars files, or generated deployment credentials under any circumstances. |
| Tests | Add or update tests when behavior changes. The suite lives under test/ and uses Vitest. |
| Migrations | Database schema changes require a new migration file in db/migrations/ following the existing naming convention. |

<h2 id="security">Security Policy</h2>

Please do not open public issues for security vulnerabilities. Report security issues privately so they can be addressed before public disclosure.

### Reporting

| Method | Contact | Description |
| --- | --- | --- |
| Email | `me@devarshi.dev` | Preferred channel for vulnerability reports. |
| GitHub | Private reporting | Use GitHub's private security advisory feature if enabled on the repository. |

### Security-Sensitive Areas

- GitHub webhook signature verification
- GitHub App private key handling
- OAuth state and session storage in Cloudflare KV
- Dashboard user allowlist enforcement
- CSRF protection on unsafe dashboard/API requests
- Dashboard-managed LLM provider key encryption
- Cloudflare API token scope for model catalog refresh
- Database connection string handling
